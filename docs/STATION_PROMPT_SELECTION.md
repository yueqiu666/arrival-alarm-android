# 自动车站提示技术选型

- 日期：2026-09-09
- 状态：`APPROVED_FOR_FIRST_SLICE`；仅确定首个实现范围，不代表已引入依赖、权限或运行能力
- 关联需求：[自动车站提示设计](STATION_PROMPT_DESIGN.md)
- 关联决策：ADR-0006

## 要解决的问题

用户明确开启自动车站提示后，应用默认全天运行，在接近地铁站或铁路客运站时只发送“是否设置到站提醒”的通知。用户可以暂停、关闭或设置运行时间段。应用不自动选择目的地，也不自动创建到站提醒。

首批目标是中国大陆常见国产 Android 手机，不能把 Google Play 服务作为必备条件。用户接受持续通知；拒绝必要位置授权、撤销授权或系统无法后台运行时，自动提示必须显示为关闭或不可用，手动到站提醒继续可用。

## 已核对的事实

1. 当前 Manifest 已声明大致/精确位置、通知、`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_LOCATION` 和 `location` 前台服务类型；未声明 `ACCESS_BACKGROUND_LOCATION`。
2. Android 官方文档说明：运行中的 `location` 前台服务属于前台位置访问；应用进入后台或锁屏后仍保留该访问，且系统以持续通知提示用户。该路径要求用户先从可见 Activity 启动服务。
3. Android 官方文档也说明：地理围栏属于后台位置访问场景；Android 10 及以上必须声明并在运行时获得 `ACCESS_BACKGROUND_LOCATION` 才能请求该授权。
4. 旧 `TrackingService.maybeCheckNearbyStation` 通过系统 `Geocoder` 反查地址，再以站名字样匹配。这不提供稳定车站 ID、站体/出入口关系、可解释边界或可靠的离开与重入判定，不能恢复使用。
5. 当前地点搜索已会把查询文字及可选附近坐标交给外部服务；自动提示若使用第三方定位/围栏 SDK，会新增一条独立数据流，不能沿用现有 P0-2 结论。

## 候选路径

| 路径 | 权限与运行方式 | 数据流 | 主要优点 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 原生定位前台服务 + 本地车站目录 | 用户在可见界面开启；使用现有 location FGS 和持续通知；运行中的会话不依赖 `ACCESS_BACKGROUND_LOCATION` | 当前定位由系统提供；车站匹配和距离判断在本机完成 | 不依赖 GMS 或第三方定位 SDK；新增外部接收方最少；规则、停止和状态可控 | 服务被系统终止后不能承诺静默恢复；耗电、国产系统保活和站点数据覆盖仍需真机验证 | **推荐作为成都首个垂直切片** |
| B. 国内定位/地理围栏 SDK | 围栏通常涉及后台位置；SDK 文档还要求本地服务保持存活 | SDK、车站查询和可能的设备标识处理须单独披露 | SDK 可能提供围栏和 POI 能力 | 新依赖、密钥、供应商数据处理、授权、成本、版本兼容和商店政策均未核实 | 保留为后续比较项，不在首个切片引入 |
| C. Google Geofencing | 依赖 Google Play 服务并需要后台位置 | Google Play 服务路径 | Android 生态常见实现 | 不符合首批国产 Android 的必备兼容要求 | 不采用为首批路径 |
| D. 旧 Geocoder 地址匹配 | 依赖持续定位和系统反查 | 系统 Geocoder 的实际网络接收方未知 | 无新 SDK | 站点身份、边界、去重和异步生命周期均不可靠 | 拒绝 |

## 建议方案：A 的受限首个切片

在取得项目负责人批准后，成都首个切片采用“用户启动的原生 location 前台服务 + 本地、版本化的成都车站目录”。自动检测期间只保留一个用户可见的持续通知，并提供暂停与关闭入口。车站记录必须至少包含稳定 ID、名称、设施类型、坐标、坐标系、数据来源、数据版本和授权状态；站体与出入口如何归并需由数据验证决定。

项目负责人已确认首个目录覆盖成都市范围内的全量地铁站。这里的“全量”不包含铁路客运站、公交站、道路 POI 或全国车站；站点完整性必须以可复查的来源、提取日期和逐线核对结果证明，不能仅由一次关键词搜索宣称覆盖。

该方案不是“保证全天永远运行”：它仅在前台服务实际存活、定位可用且用户开关及时间规则允许时运行。服务被系统或厂商终止、权限被撤销、定位关闭或位置质量不足时，检测状态必须转为不可用；不能用已保存的开关表示正在检测，也不能自动拉起一个位置服务来伪装恢复。

此切片不新增 `ACCESS_BACKGROUND_LOCATION`，也不注册地理围栏。用户拒绝精确位置、通知或前台服务无法启动时，自动提示关闭或不可用，手动到站提醒保留。若后续要求在服务未运行、进程终止或重启后仍自动恢复，必须重新评估后台位置、开机/调度机制、Android 后台启动限制、隐私披露与商店政策，不能把它并入本切片。

## 时间段设置边界

“在某时段内不读取位置”可以由一个已经运行的服务立即实现；但“服务在未运行时到达开始时刻后自动启动”是另一项后台调度能力。Android 的后台启动限制可能阻止它直接启动 location 前台服务，且可能需要更广的授权或降低为非精确、非保证的触发。

项目负责人已确认：时间段只控制已经运行的自动提示。时间段开始时，若服务已经停止、被系统终止或从未启动，自动提示保持关闭；用户可自行打开应用并启动它。首个切片不实现或宣称“定时自动恢复”。

默认全天运行不受此限制：它由用户在可见界面开启后维持前台服务会话。未来若要求在应用未运行时按时间表自动重新开始，须作为独立 P0 重新评估后台调度、后台位置权限、Android 后台启动限制与商店政策。

## 首个切片的验收边界

1. 车站数据只来自已记录来源和授权状态的成都地铁目录；未有合格数据时，不能发布或扩大覆盖范围。
2. 在同一服务会话中，靠近已知车站只提示一次；“本次不用”在确认离开和重新靠近前保持抑制。
3. 暂停、关闭、权限撤销、定位不可用、服务启动失败或服务终止后，通知和设置页不得显示“正在检测”。
4. 已确认的到站提醒不因自动检测暂停、关闭或失败而停止。
5. 纯 Java 测试覆盖车站访问状态、去重、抑制、重入、时段守卫、权限/服务失败及迟到事件；真机验收继续按既定计划暂缓。
6. 引入车站数据或 SDK 前更新 P0-2 数据流、`PRIVACY.md`、应用内披露和 ADR；引入 SDK 还需检查许可证、依赖校验、体积和供应链。

## 仍为 UNKNOWN 的事实

- 可用于产品的成都地铁站数据来源、许可、更新机制、覆盖范围与坐标系。
- 车站进入、离开和重入的可解释阈值，以及精确位置是否足以支持这些边界。
- 小米设备上持续前台定位的耗电、被终止概率、锁屏通知和省电策略影响。
- 多久未收到定位应显示为不可用，以及服务终止时用户何时能看到该状态。
- 第三方 SDK 是否能在不扩大数据处理和权限风险的前提下带来足够收益。
- 任何实际发行渠道对长期 location FGS 与后台位置组合的接受程度。

## 官方依据

- [请求位置信息权限](https://developer.android.com/develop/sensors-and-location/location/permissions?hl=zh-cn)，于 2026-09-09 核对：运行中的 `location` 前台服务在应用进入后台或锁屏后保持前台位置访问；地理围栏需要后台位置；Android 10 及以上的后台位置需声明 `ACCESS_BACKGROUND_LOCATION`。
- [高德 Android 定位 SDK 地理围栏](https://lbs.amap.com/api/android-location-sdk/guide/additional-func/geo-fence)，已于 2026-09-07 记录：其文档将本地服务存活作为后台围栏检测约束。该页面版本、SDK 当前行为和隐私处理均须在实际选型时复核。
- [Google Play 后台位置政策](https://support.google.com/googleplay/android-developer/answer/9799150?hl=zh-cn)，后台位置只可在核心功能必要且满足政策要求时申请；Console 审核材料仍按项目决定暂缓。
