# 自动车站提示设计

- 日期：2026-09-07
- 产品目标：已由项目负责人确认
- 实施方案：待定；本文件不是已实现行为或发布通过证明
- 关联决策：ADR-0006
- 候选方案评审：[自动车站提示技术选型](STATION_PROMPT_SELECTION.md)

## 已确认的目标

帮助忘记设置到站提醒的用户：接近地铁站或高铁站时收到“是否设置到站提醒”的提示，点击后选择目的地和提醒半径，主动开始到站守候。未打开应用界面或锁屏时也希望收到通知。

首批面向中国大陆常见国产 Android 手机，不能假定设备具备 Google Play 服务。目标不是识别用户已经购票、进站或乘车；靠近车站只能提供一个候选场景。

项目负责人接受开启自动提示后显示可暂停的持续运行通知。常驻通知是用户可见状态和控制入口，不是持续存活、低耗电或审核通过的保证。

首轮验证城市已确认为成都。该选择用于数据和场景验证，不代表全市车站已覆盖，也不把现有目的地搜索限制为成都。

后续真机验证使用小米手机。具体型号、系统版本和连接操作留到恢复设备验收时记录，不作为当前文档、数据流核对或纯逻辑工作的前置条件。已有小米/HyperOS 工作流见 [P0-2 工作流](play/p0-2-workflow.md)；选择测试设备不等于启动小米商店发布。

真实位置读取、权限授权和后台执行限制仍然适用。距离判断可在本机完成不等于不需要后台位置权限，也不证明定位 SDK 不会向服务方发送数据。

## 已确认的用户控制与重入规则

- 用户可在设置中开启、暂停或关闭自动车站提示。关闭后停止该功能的检测和提示，已有的到站提醒任务继续执行。
- 自动车站提示在用户明确开启后默认全天运行；用户可随时暂停、关闭，或设置只在自己选择的时间段运行。暂停、关闭或非运行时段都不应继续取得用于车站提示的位置或发送新提示。
- 时间段开始时，若自动提示服务未运行、已被系统终止或从未启动，自动提示保持关闭；用户可自行打开应用并启动它。首个切片不承诺按时段静默自动恢复。
- 点击“本次不用”后，同一次接近该车站期间不再提示；即使用户继续在附近停留，也不能仅因时间经过而再次提示。
- 确认用户离开该车站区域后，下次重新靠近时自动恢复提示资格，无需用户重新开启功能。
- “确认离开”不能直接等同于一次定位跳变、定位暂时缺失、SDK 重复事件或检测订阅重建。离开与重入的判定阈值仍需设计和验证，当前没有设定数值。

最低验收场景（尚未执行）：

| 场景 | 预期行为 |
| --- | --- |
| 靠近车站，收到提示并点击“本次不用”，之后仍停留在附近 | 保持本次抑制，不重复提示 |
| 本次抑制期间出现边界定位漂移或重复进入事件 | 不直接恢复提示资格 |
| 本次抑制后确认离开，再确认重新靠近 | 可以产生一次新的车站提示 |
| 关闭自动提示后出现迟到事件 | 不发新提示；已有到站任务不被误停 |

## 成都首轮验证范围

首个目录范围已确认：成都市范围内全量地铁站。铁路客运站、公交站、道路 POI 和全国车站均不在本轮范围内。下列项目仍是数据和行为验证样本，尚未核验 POI、坐标、边界或执行设备测试：

| 场景 | 候选样本或选取方式 | 要验证的问题 |
| --- | --- | --- |
| 地铁换乘站 | 天府广场站及不同出入口 | 站体与出入口不能直接当成互不相关的新访问，需确定归并方式 |
| 大型交通枢纽的地铁站 | 成都东客站及周边地铁设施 | 核验站体、出入口与相邻场所的归并及提示行为 |
| 路过或常住站旁 | 从上述车站相邻道路、商场或住宅选点 | 验证“本次不用”期间持续抑制及关闭功能的行为 |
| 离开后重新接近 | 对同一已核验车站构造事件序列 | 验证真正重入可以再提示，定位漂移不会重复提示 |

数据核验需记录提供方、稳定 POI ID、站名、设施类型、站体与出入口关系、城市或行政区、原始坐标系、转换方式、查询日期和使用授权。检测半径及边界必须另行验证，不根据站名或示例坐标推定。

当前 `AmapPlaceSearch` 使用输入联想接口，供目的地候选查询；这不能证明已经拥有完整或可持续更新的车站目录。车站数据方案仍需核对按设施类型查询、数据覆盖、授权、配额和失效处理。选定数据源前不批量采集，不把候选样本写成已验证的生产数据。

## 权限边界

“全天默认运行”仅指用户在设置中明确开启后的默认策略，不是首次安装后静默开始定位。自动车站提示要在应用界面不可见或锁屏时发现接近车站，通常需要精确位置、通知，以及可在后台持续获得位置的执行与授权方案；具体是否使用 Android 后台位置权限、location 前台服务或候选 SDK 的围栏能力，尚未选型。

当前实现没有 `ACCESS_BACKGROUND_LOCATION`。现有用户主动启动的到站守候和未来自动车站提示不能共用“当前未申请后台位置”的结论。若方案需要声明后台位置，必须满足以下边界后才能实施：

1. 用户先在可见界面主动打开自动提示，清楚知道会在未打开应用时使用位置，并能在同一处暂停、关闭和设置时段。
2. 只在自动提示实际开启且处于运行时段时保持检测；关闭、暂停、时段结束、权限撤销或服务失败时停止，并在界面和持续通知中显示真实状态。
3. 拒绝后台位置或设备限制后台运行时，不伪称“正在检测”；自动提示应显示不可用原因，用户仍可使用已有的手动到站提醒。
4. 选定 SDK 后重新核对其位置、设备标识及网络传输，更新数据安全资料、隐私政策和用户同意文案；本机距离计算不等于 SDK 不会上传位置。

Android 和部分国产系统可以提供此类授权，但系统授予、厂商省电策略和商店审核是不同问题。Google Play 对后台位置要求核心功能必要性、显著披露和审批材料；其前台服务政策也在收紧地理围栏用途。因此“核心功能”可作为申请理由，但不是必然获批或保证长期后台存活的凭证。首批发行渠道尚未确定，不能提前承诺某个渠道会接受该权限组合。

项目负责人已确认：用户拒绝用于后台自动提示的必要位置授权时，自动提示必须明确显示为关闭或不可用，不能在应用关闭后继续声称会发现车站；用户仍可手动设置和使用到站提醒。该降级规则适用于用户拒绝权限、后续撤销权限和系统不允许当前后台运行三类情况。具体界面文字、跳转系统设置的时机和各 Android 版本的授权步骤留待方案选型后确定。

## 当前实现证据

- 当前 Manifest 和权限门禁没有启用后台位置或开机恢复；Activity 与服务启动时会清除已延期的自动检测设置。
- 旧 `TrackingService.maybeCheckNearbyStation` 把位置交给系统 Geocoder，再用 `StationSignalMatcher` 匹配地址中的站名。这不能证明用户进入了某个具有准确坐标和边界的车站范围。
- 旧检测和新手动守候调用链已经分离，恢复一个开关不足以恢复完整能力。
- 现有 `ReminderRuntime`、Provider 集合和运行代次提供可参考的生命周期建模，但尚未验证新的自动提示流程。
- 当前搜索和坐标导入本身已涉及关键词、附近位置和目的地坐标处理；P0-2 仍需逐项核对这些实际数据流。

## 候选路径与证据边界

| 路径 | 已知条件 | 当前判断 |
| --- | --- | --- |
| Google Geofencing API | 依赖 Google Play 服务；目标 API 29 及以上需要后台位置权限；后台事件可能延迟 | 不作为首批设备的必备路径，可作为未来兼容方案 |
| 国内定位及地理围栏 SDK | 高德提供基于 POI、圆形和多边形的围栏；官方文档要求后台检测时保持本地服务存活 | 可评估，但未证明当前 Android 版本、目标机型和发行渠道下可靠可用 |
| 重新启用旧持续定位与地址匹配 | 缺少可靠车站边界，且仍有服务存活、权限、耗电和异步生命周期问题 | 不作为直接恢复方案 |

高德地理围栏页面最后更新于 2022-04-24，本次于 2026-09-07 读取。其“后台需要服务存活”是明确约束，但文档存在接口不等于 Android 16 或所有国产机型都已验收。应核对候选 SDK 的当前版本、隐私合规说明、授权和目标机型证据后再选型。

Google Play 官方预告从 2027-01-27 起移除 geofencing 作为获准的前台服务用途。国内 SDK 不自动豁免该政策；目标设备地区和实际发行渠道必须分别确认。现有目的地半径触发也需核对政策适用边界。

## 建议的产品边界（尚未实施）

1. 用户首次明确开启自动车站提示并完成必要授权；不要求每次出行都先打开应用，但首次授权和实际运行条件不能省略。
2. 明确车站数据范围、坐标系、来源、授权与更新方式，再注册或维护检测区域。
3. 进入候选车站区域时只发送设置提醒，后台不强制弹出 Activity，不自动猜测目的地或开始到站任务。
4. 用户点击后进入目的地选择，忽略提示不创建到站任务。
5. 自动检测和到站任务分别建模；实现上述已确认的关闭行为，不误停用户已确认的到站任务。
6. 按上述已确认的“本次不用”和重入行为设计去重及误触发控制；位置质量和边界判定参数由可解释规则和测试确定，不直接沿用旧阈值。
7. 权限撤销、系统限制或服务不可用时不显示“正常检测”。重启、进程终止及强制停止分别验收，不承诺所有情况下自动恢复。

## 当前可推进的工作

已确认的核心目标、国产 Android 优先、持续通知、用户开关、本次抑制和重入规则、成都及小米无需重复询问。用户要求减少重复澄清；只有会改变当前方案且无法从记录或源码确定的产品取舍才继续提问。当前先完善 [P0-2 数据流草稿](play/data-safety.md)，具体设备与商店操作继续暂缓。

- 完成当前代码与候选 SDK 的数据流清单，分别记录源码事实和运行时未知项；不把尚未实现的能力写成当前隐私政策事实。
- 核对自动检测的运行契约：谁持有订阅、何时停止、失败如何显示、旧回调如何失效。
- 方案确定后建立纯逻辑回归测试：重复进入、停留抖动、忽略提示、已有任务、关闭开关后迟到事件、定位过旧或精度不足。
- 集成前明确 SDK 版本、依赖和权限变更范围；集成后运行构建、Lint、合并 Manifest 和数据流检查。原权限门禁需要按新批准范围演进，不能简单删除。
- 真机、抓包、锁屏省电、重启和实际通知验收，以及商店材料提交按用户决定暂缓，保留为未完成项。

当前 P0-1 签名工程继续作为基础；P0-2 需按新功能重审权限与数据；P0-3 需分别验证自动检测和到站任务生命周期。P0-4 至 P0-8 及其他历史问题仍保留，产品方向改变不构成问题关闭。
